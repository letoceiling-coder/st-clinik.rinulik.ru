## 1. Исходное состояние

Кратко по аудиту (подробности — в отчёте аудита):

| Область | Готовность | Ключевые пробелы |
|---|---|---|
| Каталог, поиск, карточки, сравнение | ~75% | гео-город, часть фильтров, «ближайший слот» |
| Онлайн-запись | ~25% | это заявка, а не бронь слота; нет защиты от гонок в БД |
| Авторизация | ~40% | нет восстановления пароля, верификации email, Яндекс/VK/MAX |
| Уведомления | ~25% | только in-app; нет email/SMS/мессенджеров и напоминаний |
| Кабинет клиники | ~55% | нет сотрудников, регистрации организации, тарифа, платежей |
| Монетизация | ~15–60% | тарифы без лимитов и без влияния на каталог; эквайринг **Т‑Банк** (ЮKassa не используется) |
| Админка: финансы, отчёты, аналитика | ~5% | отсутствуют |
| Инфраструктура | ~15% | SQLite, нет очередей, планировщика, бэкапов, мониторинга, SSR |

Стек: Laravel 13 (PHP 8.3), Inertia v3 + React, Vite, Docker Compose на `93.189.229.117`, смежный сервис `parser.rinulik.ru`.

## 2. Архитектурные решения и готовые компоненты

### 2.1. Целевая инфраструктура (Docker Compose, проект `st-clinik`)

| Контейнер | Образ | Назначение |
|---|---|---|
| `st-clinik-app` | свой (PHP 8.3-FPM) | веб-запросы |
| `st-clinik-web` | nginx | статика + прокси на FPM |
| `st-clinik-pg` | `pgvector/pgvector:pg17` | **PostgreSQL 17 + pgvector** (БД и векторный поиск ассистента) |
| `st-clinik-redis` | `redis:7-alpine` | кэш, сессии, очереди, блокировки, PKCE VK ID |
| `st-clinik-horizon` | свой (тот же образ) | обработчики очередей (Laravel Horizon) |
| `st-clinik-scheduler` | свой (тот же образ) | `php artisan schedule:work` |
| `st-clinik-ssr` | свой (Node 22) | Inertia SSR (`bootstrap/ssr/ssr.js`) |

Принципы:
- PostgreSQL и Redis доступны **только во внутренней сети** compose, наружу порты не публикуются.
- Отдельные тома: `st-clinik-pg`, `st-clinik-redis`, существующие `st-clinik-storage`, `st-clinik-public`. Том `st-clinik-sqlite` сохраняется 30 дней после переезда как точка отката.
- Деплой через сборку образа (без выборочного `docker cp` файлов в работающий контейнер), миграции — отдельным шагом, `php artisan horizon:terminate` после деплоя.
- **Staging** на том же сервере: `staging.st-clinik.rinulik.ru`, compose-проект `st-clinik-staging`, свой порт, свои тома, своя БД. Нужен для модерации MAX-бота, тестов платежей и приёмки фаз.

### 2.2. Готовые проверенные решения

| Задача | Решение | Почему |
|---|---|---|
| OAuth Яндекс | `laravel/socialite` + `socialiteproviders/yandex` | официальный Socialite + провайдер из экосистемы SocialiteProviders |
| OAuth VK ID 2.1 (PKCE) | `movemoveapp/vkid` **или** собственный провайдер (~150 строк) | `socialiteproviders/vkid` требует PHP 8.4, у нас 8.3; перед установкой проверить требования `movemoveapp/vkid` |
| Вход через MAX | собственная реализация по документации MAX (deep link + webhook `bot_started`, проверка `initData` для Mini App) | готового пакета для Laravel нет; протокол простой и документирован |
| Очереди | Redis + `laravel/horizon` | мониторинг очередей, ретраи, метрики |
| Уведомления | Laravel Notifications + свои каналы `MaxChannel`, `VkChannel`, `SmsChannel` + `laravel-notification-channels/webpush` | единый интерфейс, очереди, предпочтения пользователя |
| Бэкапы | `spatie/laravel-backup` | `pg_dump` + файлы → S3, ротация, уведомления о сбоях |
| Ошибки | `sentry/sentry-laravel` (облако Sentry или self-hosted GlitchTip) | алерты по ошибкам приложения |
| Мониторинг | `laravel/pulse` + внешний uptime-мониторинг (Uptime Kuma на сервере) | производительность, медленные запросы, доступность |
| Векторный поиск | PostgreSQL `pgvector` + `pgvector/pgvector` (PHP-пакет для Eloquent) | без отдельного сервиса; гибрид с полнотекстовым поиском PostgreSQL |
| LLM/эмбеддинги | OpenRouter (OpenAI-совместимый API: `/api/v1/chat/completions`, `/api/v1/embeddings`) через собственный тонкий клиент на `Http` **или** `prism-php/prism` после проверки совместимости с Laravel 13 | не привязываемся к одному поставщику моделей |
| Excel-отчёты | `openspout/openspout` (уже установлен) | потоковая запись больших XLSX/CSV |
| Редактор КП | TipTap (React) | WYSIWYG с переменными-плейсхолдерами |
| Короткие ссылки | собственный маршрут `/o/{code}` | контроль, трекинг, без внешних сокращателей |

Все новые зависимости — в разделе [6](#6-новые-зависимости), устанавливаются только после согласования.

### 2.3. Хранение ключей и секретов

Уже реализовано: `IntegrationSettings` шифрует секретные поля через `Crypt` (ключ — `APP_KEY`), в UI отдаются только маски. План доработки:

1. Все ключи (OpenRouter, парсер, MAX, VK, Яндекс, SMS, SMTP, S3, Sentry, **Т‑Банк (эквайринг)**, VAPID) — только в БД через админку; `.env` — fallback для первичного запуска. **ЮKassa не используется.**
2. Кнопка **«Проверить подключение»** у каждой интеграции (реальный тестовый вызов API), статус и время последней проверки.
3. Журнал аудита: кто и когда изменил интеграцию (значения секретов не логируются).
4. Право `integrations.manage` — только у суперадмина.
5. Ротация `APP_KEY` — через `APP_PREVIOUS_KEYS` (Laravel поддерживает расшифровку старым ключом), процедура описывается в `docs/server-and-deploy.md`.
6. После сохранения интеграции — автоматический `horizon:terminate` (долгоживущие воркеры перечитают настройки). Это важная деталь: иначе очереди будут работать со старыми ключами.

## 3. Ограничения внешних платформ

Это нужно учесть **до** начала разработки, чтобы не обещать невозможное.

### 3.1. MAX

- Классического OAuth для сайтов **нет**. Вход реализуется через бота: сайт генерирует одноразовый код → пользователь открывает `https://max.ru/<бот>?start=<код>` → MAX присылает webhook `bot_started` с этим кодом и `user_id` → сайт авторизует сессию. В Mini App — через подписанные данные `window.WebApp.initData` (HMAC-SHA256 с токеном бота).
- Бот **не может написать первым**: сообщения возможны только пользователям, которые запустили бота. Значит, рассылки в MAX — только подписчикам бота.
- Для бота и Mini App нужен **верифицированный профиль организации (ИП/ООО)** на платформе MAX для партнёров и **модерация бота**. Владельцем бота должен быть заказчик.
- Mini App без бота подключить нельзя: Mini App настраивается в карточке бота (URL сайта).
- API: `https://platform-api2.max.ru`, токен в заголовке `Authorization`. На сервере нужно установить **корневой сертификат Минцифры** в доверенные.
- Следствие для КП: отправить КП организации в MAX «холодно» нельзя. Канал MAX для КП — только ручной (оператор отправляет со своего аккаунта, система готовит текст и ссылку) или если представитель клиники сам запустил бота.

### 3.2. VK

- Вход: VK ID OAuth 2.1 с обязательным PKCE.
- Сообщения от сообщества пользователю — только после **разрешения пользователя** (виджет «Разрешить сообщения от сообщества» на сайте, событие `message_allow` в Callback API или пользователь написал первым). Список разрешивших хранится у нас — API его не отдаёт.
- Сообщество не может писать другому сообществу. Следствие для КП: канал VK — ручной (оператор пишет в сообщество клиники, система готовит текст и отслеживает переходы по ссылке).

### 3.3. Яндекс

- Вход: Яндекс ID OAuth (`login:email`, `login:info`, при необходимости `login:default_phone`).
- Публичного мессенджера с API для рассылок пользователям у Яндекса нет. «Уведомления подписавшимся через Яндекс» реализуются как: **email на подтверждённый адрес Яндекс ID** + **Web Push** (поддерживается Яндекс Браузером, Chrome, Edge, Firefox; Safari iOS — только для сайта, установленного на экран «Домой»).

### 3.4. Данные парсера (проверено тестом, см. приложение A)

- В карточках организаций **нет email** и **нет ссылок на MAX**. Есть телефоны, сайт, `socialLinks` (vk, telegram, whatsapp, ok, youtube), `messagingLinks`.
- Email придётся получать отдельно: задачей `page.html` по сайту клиники (страница контактов) с извлечением адресов, с отметкой источника.
- Быстрый режим `yandex.orgs` отдаёт «сырые» данные: адрес слипается с этажом («Ставропольэтаж цокольный»), `hours` — это статус («Закрыто до завтра»), а не график, `categories` пустые, в поле `website` может быть ссылка на Telegram, телефоны бывают пустыми. Для импорта нужна нормализация, а для полноты — полные карточки (`organizations.agent` или запрос `GET /api/v1/organizations/:id` с `fields=full`).
- Фильтр `category` в `/api/v1/organizations` ищет **точное** значение: в базе категория сохранена как «стоматолог», запрос `category=стоматология` возвращает 0. Использовать рубрики («Стоматологическая клиника») или значения из `/organizations/categories`.
- Сеть клиник приходит отдельными карточками с одинаковыми телефоном и сайтом (пример: «ДК», два адреса, один телефон) — нужна группировка в одну организацию с филиалами.

### 3.5. SMS и email-рассылки КП

- КП — это реклама. По ст. 18 ФЗ «О рекламе» распространение рекламы по сетям электросвязи (SMS, звонки, email) требует **предварительного согласия адресата**; риск штрафа для юрлица — до 500 000 ₽ за эпизод. Решение о «холодных» SMS/email принимает заказчик (п. 3.1 договора — юридическая экспертиза не входит). Технически система поддержит: стоп-лист, отписку в каждом сообщении, журнал отправок, лимиты.
- SMS: нужна регистрация буквенного имени отправителя у провайдера (обычно 1–3 недели и абонентская плата за имя у операторов).
- Email для КП — **отдельный домен/поддомен и отдельный SMTP** (не транзакционный), SPF/DKIM/DMARC, прогрев, суточные лимиты, заголовок `List-Unsubscribe`.

### Фаза 1. Инфраструктура и перенос на PostgreSQL

**Срок:** 7–8 дней.

#### 1.1. Подготовка кода к PostgreSQL (2 дня)

- Поиск по `like` в админке и сервисах (`UserController`, `ClinicController`, `ReviewController`, `DictionaryController`, `SearchService`, репозитории) → `whereLike(..., caseSensitive: false)` (в PostgreSQL `LIKE` чувствителен к регистру, Laravel превратит это в `ILIKE`).
- Проверить сырые выражения: `orderByRaw('... is null')`, `CASE WHEN`, `selectRaw(count/avg)` — переносимы; `orderByRaw` с подстановкой ID → `whereIn` + `orderByRaw` с биндингами.
- Булевы поля: SQLite хранит 0/1 — проверить приведение (`casts`) у всех моделей с флагами.
- JSON-колонки → в PostgreSQL `jsonb` (новые миграции используют `jsonb()`), индексы GIN там, где есть фильтрация по JSON.
- Тесты: PHPUnit запускается на PostgreSQL (отдельная тестовая БД), SQLite оставляем только для быстрых локальных прогонов, если нужно.

#### 1.2. Контейнеры (1,5 дня)

- `deploy/Dockerfile`: `pdo_pgsql`, `pgsql`, `redis` (pecl), `pcntl` (уже есть), клиент `postgresql-client` для `pg_dump`.
- `deploy/docker-compose.yml`: сервисы `pg`, `redis`, `horizon`, `scheduler`, `ssr` (см. 2.1), healthcheck-и, `depends_on: condition: service_healthy`.
- Переменные: `DB_CONNECTION=pgsql`, `CACHE_STORE=redis`, `SESSION_DRIVER=redis`, `QUEUE_CONNECTION=redis`.
- Сертификат Минцифры — в образ (`/usr/local/share/ca-certificates` + `update-ca-certificates`) для вызовов MAX API.

#### 1.3. Перенос данных SQLite → PostgreSQL (2 дня)

Команда `php artisan db:migrate-to-pgsql` (собственная, в репозитории), алгоритм:

1. `php artisan migrate --database=pgsql` на пустой БД — схема создаётся миграциями Laravel (а не копируется из SQLite).
2. Список таблиц в порядке зависимостей внешних ключей; на время копирования `SET session_replication_role = replica`.
3. Копирование чанками по 1000 строк с сохранением `id`; приведение типов: булевы 0/1 → `true/false`, JSON-строки → `jsonb`, даты — как есть (UTC).
4. Сброс последовательностей: `SELECT setval(pg_get_serial_sequence('table','id'), COALESCE(MAX(id),1))` по всем таблицам.
5. Проверка: количество строк по каждой таблице, контрольные суммы выборки (хэш от `id` + ключевых полей), отчёт в консоль и в файл.
6. Таблицы `sessions`, `cache`, `jobs` не переносим — они уходят в Redis.

Генеральная репетиция — на копии production-SQLite локально и на staging. Прогон всего набора тестов и ручной смоук-тест ключевых страниц.

#### 1.4. Переключение production (0,5 дня, окно ~15 минут)

1. Уведомление; `php artisan down --secret=...`.
2. Копия файла SQLite (`database.sqlite` → `database.sqlite.pre-pg-YYYYMMDD`).
3. `db:migrate-to-pgsql` → отчёт сверки без расхождений.
4. Переключение `.env` на `pgsql`, `config:cache`, `horizon:terminate`, `up`.
5. Смоук-тест: главная, каталог города, клиника, вход, кабинет клиники, админка, заявка, оплата (тестовый режим).
6. **Откат** (если что-то не так): вернуть `DB_CONNECTION=sqlite`, `config:cache` — 5 минут; SQLite-файл не тронут.

#### 1.5. Бэкапы, мониторинг, CI (1,5 дня)

6. **Статусы:** `new`, `pending`, `confirmed`, `rescheduled`, `completed`, `cancelled`, `no_show`; таблица истории `appointment_status_history` (кто, когда, из какого статуса в какой, комментарий).

10. **Заявки** остаются как отдельный канал («перезвоните мне»), но больше не меняют статус автоматически.

**Приёмка:** параллельный тест на одну и ту же ячейку — создаётся ровно одна запись; полный сценарий пациента из п. 93 ТЗ проходит до шага «увидеть запись в кабинете».

### Фаза 7. Парсер организаций

**Срок:** 8–10 дней. Доступ — **только администратор** (право `parser.manage`, по умолчанию только у суперадмина). Все действия — в журнал аудита.

#### 7.1. Принцип
Спарсенные организации **никогда не публикуются автоматически**. Путь: парсер → промежуточная таблица → проверка админом → импорт в **черновик** (`status=draft`, `owner_id=null`, `source=parser`) → (опционально) КП и демо → клиника подключается → модерация → публикация.

#### 7.2. Раздел «Парсер» в админке
1. **Задачи:** форма запуска — тип (`yandex.orgs` — быстро; `organizations.agent` — полные карточки), город, категория/запрос, количество (1–500), фото да/нет, лимит стоимости (USD). Idempotency-Key = хэш параметров + дата.
2. **Мониторинг:** статус и прогресс (опрос `GET /api/v1/tasks/:id` из очереди каждые 5 секунд; SSE — опционально), отмена задачи, история задач (кто запустил, сколько стоило, сколько найдено).
3. **База парсера:** просмотр уже собранных организаций (`/api/v1/organizations` с фильтрами city, category, hasPhone, hasWebsite, minRating, minReviews), счётчики по городам и рубрикам — без запуска новых задач.
4. **Инкрементальная синхронизация:** ежедневно по `updatedSince` (scheduler), только обновление промежуточной таблицы, без изменения уже отредактированных черновиков (поля, изменённые вручную, помечаются и не перезаписываются).

#### 7.3. Промежуточная таблица `parsed_organizations`
`external_id` (уникальный, id Яндекса), `source`, `raw` (jsonb — исходная карточка целиком), нормализованные поля (название, город → `city_id`, адрес, этаж, координаты, телефоны E.164, сайт, соцсети, мессенджеры, график, рейтинг и отзывы Яндекса, рубрики, услуги, цены), `group_key` (для объединения сети), `match_clinic_id` (найденный дубль), `status` (`new|reviewed|imported|ignored|duplicate`), `last_synced_at`, `parser_task_id`.

#### 7.4. Нормализация
- Адрес: отделение «этаж …», «офис …» в отдельное поле; удаление города из конца строки.
- Телефоны → E.164, удаление дублей.
- `website`: если это t.me / vk / wa.me — переносится в соцсети.
- График: из `hoursSchedule` (полная карточка) в формат `clinics.schedule`; строка `hours` быстрого режима не используется как график.
- Услуги: справочник соответствий «название из Яндекса → наша услуга» (`service_mappings`), автоподбор по нормализованному названию, неизвестные — в очередь сопоставления админом.
- Особенности (`attributes`): `for_children`, `uni_medic_adult`, `dental treatment in installments`, `payment_method`, `car_park` и т.д. → `clinic_property_types` через таблицу соответствий.
- Цены (`products`) → прайс черновика с пометкой «по данным Яндекса».
- Фото: загрузка в наше хранилище (S3) в фоне, не более N штук, с указанием источника.
- Отзывы Яндекса **не импортируются** как отзывы платформы (права на контент и достоверность); рейтинг Яндекса можно хранить для внутренней аналитики и персонализации КП.

#### 7.5. Дубликаты и сети
- Совпадение по `yandex_org_id` → обновление.
- Совпадение по телефону, сайту или координатам (до 50 м) + похожему названию → предложение «это дубль / филиал».
- Одинаковые телефон или домен у нескольких карточек → группа «сеть»: импорт как одна организация с несколькими филиалами.

#### 7.6. Контакты для КП
`organization_contacts`: тип (`phone|email|vk|max|telegram|whatsapp|website`), значение, источник (`yandex|site|manual`), подтверждён, `do_not_contact`. Email добываются задачей `page.html` (страница контактов сайта, `includeText: true`) с извлечением адресов и `mailto:`; админ может добавить контакт вручную.

#### 7.7. Импорт

#### 7.8. Существующий код

### Фаза 9. AI-ассистент

**Срок:** 12–15 дней. Ключ OpenRouter — в центре интеграций (зашифрован в БД).

#### 9.1. Виджет
- React-компонент, загружается лениво (после взаимодействия или простоя), только на публичных страницах (не в админке и кабинете); на мобильном — полноэкранный режим.
- Потоковый ответ (SSE через `response()->stream()`), история диалога в рамках сессии/аккаунта, кнопки быстрых действий («Подобрать клинику», «Цены на имплантацию», «Записаться»), карточки клиник и врачей прямо в чате.
- Тот же движок — в MAX-боте и Mini App.

#### 9.2. Знания ассистента
1. **Опубликованные данные платформы** (только `published`): клиники, филиалы, врачи, услуги и цены, акции, CMS-страницы, FAQ. Черновики и спарсенные организации — исключены.
2. **База знаний** (админ): статьи и пары «вопрос — ответ» (правила сервиса, как записаться, ДМС, рассрочка, общие сведения об услугах).
3. **Индексация:** чанки текста → эмбеддинги через OpenRouter `/api/v1/embeddings` (например `openai/text-embedding-3-small`, 1536 измерений) → `kb_chunks` (pgvector, HNSW-индекс) + полнотекстовый индекс PostgreSQL (`russian`). Поиск — гибридный (вектор + полнотекстовый), с фильтром по городу.
4. Переиндексация — по событиям модели (observer → очередь) и полная ночью.

#### 9.3. Инструменты (function calling)
- `search_clinics(city, service, filters, sort)`, `get_clinic(slug)`, `get_prices(clinic|city, service)`, `search_doctors(city, specialty)`, `get_slots(clinic, doctor, service, date)` (после фазы 3), `search_knowledge(query)`, `create_lead(...)`.
- Инструменты только читают опубликованные данные и создают лид — никаких админских действий (защита от prompt injection).

#### 9.4. Лиды из диалога
- Ассистент уточняет город, услугу, удобное время, имя и телефон, **запрашивает согласие на обработку ПД** (явная кнопка) → `create_lead` с `source=assistant`, `conversation_id`, `city_id`.
- **Маршрутизация по городу обращения** (город из выбора на сайте или из диалога):
  1. пользователь выбрал клинику → лид в эту клинику;
  2. не выбрал → ассистент предлагает 2–3 подходящих клиники города, пользователь выбирает;
  3. «любая» → **рассылка лида сразу нескольким клиникам города** (решение от 25.10.2026): до N клиник (по умолчанию 3, настраивается в админке) среди опубликованных клиник города с флагом «Принимаю лиды ассистента», отбор по приоритету тарифа/продвижения, затем рейтингу и соответствию услуге, с ротацией, чтобы лиды распределялись равномерно;
  4. в городе нет клиник → лид в очередь администратора платформы.
- **Согласие на ПД** при множественной рассылке явно говорит, что контакты будут переданы нескольким клиникам города (до N), и перечисляет их после отправки.
- Модель: один лид пользователя (`leads`) + записи распределения `lead_dispatches` (lead_id, clinic_id, status `sent|viewed|accepted|declined|expired`, timestamps). Клиника видит лид с пометкой «Лид от ассистента, отправлен нескольким клиникам».
- Первая клиника, нажавшая «Беру в работу», фиксируется; остальным показывается «Пациента уже взяли в работу» (настраиваемо: эксклюзив первой или все могут связаться). Пользователь получает уведомление, какая клиника свяжется.
- Защита от злоупотреблений: дедупликация повторных лидов с одного телефона за 24 часа, ограничение частоты, просмотр контактов фиксируется в журнале.
- Клиники получают лид в кабинет + уведомление (email/MAX/VK по подписке), статус виден в диалоге пользователя.

#### 9.5. «Обучение» и управление (админ, право `assistant.manage`)
- Системный промпт, тон, приветствие, запрещённые темы, примеры диалогов (few-shot).
- Модель, резервная модель, температура, лимит токенов на ответ, лимит сообщений на сессию, суточный бюджет USD (при превышении — мягкое отключение с формой заявки).
- Просмотр диалогов, оценка ответов (👍/👎 пользователя и админа), кнопка «Исправить ответ» → добавляется в базу знаний как пара «вопрос — ответ».
- Статистика: диалоги, лиды, конверсия, стоимость за период, частые вопросы без ответа.

#### 9.6. Безопасность и медицина
- Дисклеймер: ассистент не ставит диагнозы и не назначает лечение; при признаках неотложного состояния — рекомендация звонить 103/112.
- Фильтр медицинских данных (`SensitiveTextGuard`) — не сохранять диагнозы в лидах.
- Ограничение частоты по IP/сессии, защита от спама, срок хранения диалогов (настраивается, по умолчанию 180 дней), обезличивание при удалении аккаунта.
- Ключ OpenRouter не попадает в браузер; все запросы — с сервера.

**Приёмка:** на тестовых вопросах ассистент находит клиники только из опубликованных, создаёт лид в клинику нужного города, бюджет и лимиты срабатывают, диалоги видны в админке.

## 7. Юридические и организационные вопросы

Решения принимает заказчик (п. 3.1, 12, 13 договора), разработка обеспечивает техническую возможность.

1. **Реклама по SMS и email** (ст. 18 ФЗ «О рекламе»): «холодные» КП без согласия — риск штрафов. Варианты: только email на публичные корпоративные адреса с отпиской / звонок менеджера с последующей отправкой КП по согласию / SMS только после согласия.
2. **Маркировка рекламы** (ERID, ОРД) для платного продвижения клиник на сайте.
3. **Верификация в MAX** — на юрлицо или ИП заказчика; владельцем бота должен быть заказчик.
4. **Имя отправителя SMS** — регистрация у провайдера на заказчика.
5. **Политика ПД** — дополнить: передача данных лида клинике, обработка диалогов ассистента, мессенджеры (MAX, VK), Web Push, трансграничная передача (OpenRouter — зарубежный сервис: в запросы к модели не передавать ПД; телефон и имя собираются формой/инструментом, а не уходят в промпт).
6. **Локализация ПД**: подтвердить, что сервер `93.189.229.117` и S3-хранилище бэкапов находятся в РФ.
7. **Контент Яндекса**: фото и тексты карточек — использование в черновиках для КП и после подключения клиники с её согласия; отзывы Яндекса не публикуются.
